# Skill — ELIRAN Phase Guardrails

## מטרה
למנוע קפיצה לשלב פיתוח לא מאושר, scope creep, והוספת פיצ'רים שלא נדרשו.

## מתי להשתמש
- לפני התחלת פיצ'ר חדש
- לפני בניית מסך חדש
- לפני הרחבת API
- לפני שינוי ארכיטקטוני
- כשבקשה נראית כמו מעבר לשלב חדש

## עקרונות חובה
- לא מתחילים שלב חדש בלי אישור.
- לא בונים UI לפני אישור Phase 1 של Data + API.
- לא מוסיפים פיצ'רים שלא נדרשו.
- אם יש ספק — שואלים לפני ביצוע.
- Airtable נשאר מקור האמת.

## צ'ק ליסט לפני תחילת עבודה
1. מה בדיוק המשתמש ביקש?
2. האם זו תחזוקה/תיקון, או פיצ'ר חדש?
3. האם זה בתוך Phase קיים או מעבר שלב?
4. האם נדרש שינוי Data/API לפני UI?
5. האם יש אישור מפורש להמשך?

## איך לפעול
- אם זו משימה בתוך Phase קיים: לבצע.
- אם זו קפיצה ל-UI לפני Data/API: לעצור ולבקש אישור.
- אם זו הרחבת scope: להציג מה נדרש עכשיו ומה אפשר לשלב הבא.
- אם חסר מידע: לשאול שאלה ממוקדת לפני מימוש.

## דוגמאות למה נחשב חריגה
- הוספת מודול חדש שלא התבקש.
- בניית מסך מלא לפני שיש שדות ונתונים מאומתים.
- יצירת שכבת data חלופית ל-Airtable.
- שינוי process עסקי בלי אישור.

## מה לא לעשות
- לא "לשפר על הדרך" בלי בקשה.
- לא להוסיף שדות, סטטוסים או זרימות חדשות בלי אישור.
- לא לעבור מ-Data ל-UI רק כי זה נוח טכנית.
